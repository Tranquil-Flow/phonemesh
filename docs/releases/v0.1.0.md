## Identity

- Android package: `org.phonemesh.app`; version **0.1.0**, version code **1**.
- Android 8.0/API 26+; target API 35. Separate **arm64-v8a** and **armeabi-v7a** APKs.
- The docs call the hub the **local hub**; this version of the app still labels its

- Public releases use a dedicated owner-controlled signer. Existing development-signed
  phones stay on their compatible development line; no uninstall/data-clear migration.
- Add-me links: `https://tranquil-flow.github.io/phonemesh/add#…`. The page and the
  Android association (`/.well-known/assetlinks.json`, public certificate only) are
  served by GitHub Pages; Android verified the link for the release APK.

## Included behavior

- Local speech-to-text, editable transcript, text over Meshtastic, and local playback;
  **audio never crosses the radio**. Speech packs are separately provisioned.
- Account-based private chats, trusted QR/link introduction and safety-picture comparison.
  Shared-channel chats are not end-to-end private account conversations.
  Private account conversations can use the pinned hub; shared-channel sending still
  requires a direct radio. In hub-only first-run setup, the guide's shared greeting
  stays queued (not hub-delivered) and may transmit after a later direct-radio connection.
  Queuing that greeting completes the guide and exposes private conversations.
- Picture messages, replies and reactions; pictures consume multiple packets. Optional
  AI upscaling weights are **not distributed** with v0.1.
- Direct radio BLE and an optional pinned-TLS local hub over local Wi-Fi or the native
  Mac BLE bridge. Hub-only Talk readiness and foreground rediscovery are in source.
- Persistent phone custody bound to a hub pin (`hub_custody`), distinct from unsigned
  port-302 observations. Private-message retries return the same stored ciphertext to
  that pinned hub until the recipient acknowledges it. Explicit duplicate submissions
  can trigger a bounded re-air; mailbox timestamps/retention are not refreshed, and
  shared-chat posts do not gain periodic retransmission. Forwarding intents, retry
  cooldowns and airtime reservations survive process restart within the limits in the
  [hub guide](../../android/hub/README.md).

## Evidence and limits

rc5 adds the hub retry recovery. Hub tests passed 76/76; the Android classes that reach
pinned hub custody passed 59/59; the isolated build from the exported source passed the
canonical checks. On two owner phones, a message whose receipt was lost while the hub was
stopped recovered through the sender's own retry: the hub aired the same ciphertext
again, the recipient showed it once, and the sender showed **Delivered** (one trial, loss
induced by stopping the hub). Android coverage for unchanged files comes from the rc4
composite below, not from a fresh whole-suite run on rc5.

The rc2 full3 development run recorded **739 passes and 8 optional skips** out of
**747 selected**. On rc3, full4 instead recorded **735 passes, 8 optional skips and
4 failures** out of **747 selected**. That failed attempt is retained, not relabelled
as green after focused checks. A later two-class run passed 114 of 115 cases and
exposed oversized-draft loss after rotation. An independently reproduced identical-text
replacement defect is now repaired; seven focused input/rotation checks passed.
Final runtime canonical checks passed. Full5 remains a failed attempt: a test fake
leaked a cancellation exception and aborted its batch, leaving 26 unique cases
unexecuted and one selector with conflicting error/success events. A deterministic
contract regression reproduced the fake's defect; after its test-only repair the
complete affected batch plus that new case passed **38/38**. Replacing the failed
batch and reconciling exact selectors with unchanged production gives **741 assertion
passes + 8 optional skips / 749 selected**. This is complete composite silent coverage,
not a new uninterrupted whole-suite pass or public-APK/physical qualification.

Earlier physical bidirectional text delivery through the BLE/pinned-TLS/USB hub path
ran on an older build and is not counted for v0.1.0. On rc3, pinned Wi-Fi authentication,
actual radio submission, automatic reauthentication after a same-pin hub restart and
persistent phone custody passed scoped checks. Recipient Delivered was not observed.
On rc4, a fresh Wi-Fi voice message reached the Pixel and owner-confirmed playback was
clear. On the emulator, the public APK installed fresh and updated the earlier public
v0.1-rc build with its data kept (that build had only reached first run).
No range/capacity, power-cut safety or exactly-once radio-delivery guarantee is made.
There is no periodic hub mailbox rebroadcast. **Reached the hub** is not recipient
**Delivered**, and neither means listened to.

Account recovery/transfer is not provided. History is local sandboxed storage, not a
separately encrypted transcript database. Keep accounts/history intact; do not clear
app data to resolve connectivity or signer errors. Background hub use and automatic
playback are opt-in, not enabled by default.

## Known limitations

- **TalkBack is not supported in v0.1.** With TalkBack on, recording can capture
  TalkBack's own speech and the send status is not announced. Phonemesh's own Read
  aloud and Listen are the supported voice path.
- **Hub Wi-Fi must use WPA2-Personal** (or be open). Android 10 phones cannot join a
  WPA2/WPA3 mixed-mode network through the app. See the [hub guide](../../android/hub/README.md).
- **No private group chats.** v0.1.0 has one shared chat per radio channel and private
  one-to-one chats; private groups are planned for the next version, as is reacting with
  any emoji (v0.1.0 offers six).
- Hub re-airs happen only when the sender retries, within three days of first storage.
  They cannot recover a message after the sender stops retrying or if the hub is down for
  the whole retry period.
