`release/v0.1.3-dev-20261105` (N1 event seam first); nothing in it is released or physically qualified.**

## Outcome and scope

A person can receive private-chat and private-group text alerts with the screen closed under an explicitly supported listening mode; a promoted group admin can manage existing members without adding everybody as personal contacts; and a qualified Windows laptop can expose the existing local hub over Bluetooth.

### Planned deliverables

- **N — Notifications and receiving lifecycle:** private one-to-one and private-group text/reply alerts; explicit opt-in listening; truthful connected/disconnected state; privacy-safe notification content and navigation.
- **G — Relayed group management:** securely deliver group control/key updates to already-admitted members without requiring every admin to have all members as personal contacts; retain consent and current group-size limit; fix the documented two-person last-admin departure behavior.
- **W — Windows Bluetooth hub companion:** one active phone initially, existing pinned-TLS hub protocol, runnable per-user foreground companion and real Windows/Android qualification.
- **R — Release integration:** data-preserving upgrade from signed v0.1.2, demo coverage, source/build/licence/size/network gates, exact artifact identity and honest supported-platform statements.

Windows is a planned workstream with an early hardware gate. If the available machine/adapter cannot support the required role, preserve the failure and request a specific owner disposition; do not silently drop support or claim an untested replacement. Independent Android work may continue. Do not let an unresolved Windows experiment automatically turn into indefinite release delay.

### Explicit non-goals

TalkBack; larger groups; username/directory or multi-account features; social recovery; automatic backup hosting; app/APK updates through hubs; local-language speech/model deployment; quiet-radio configuration or coverage wizard; cross-zone radio conversion; quantum-safe protocol changes; voice imprints; typing/seen indicators; edit/delete-for-everyone; location sharing; cloud push; notification quick reply; bulk Bluetooth updates; unattended Windows services; automatic driver/hotspot/firewall setup.

Local-language review and quiet-radio/coverage planning may proceed as separately authorized pilot preparation, not hidden v0.1.3 acceptance requirements. Existing accessibility and English/French support must not regress despite TalkBack being deferred.

## N: incoming alerts and background listening

### Current implementation and constraints

`AppCore`, `AppMailStore` and `AppGroupStore` already receive and durably store messages. `changed(Change.MESSAGES)` is a broad screen-observer signal, not a fresh-incoming-message event. The manifest already declares notification and connected-device foreground-service permissions. `HubRoaming` supplies a real opt-in foreground service; its executable lifecycle can retain/reconnect a stock-radio link, but activation currently requires a saved hub. It returns `START_NOT_STICKY`; no boot receiver provides automatic boot reception.

Do not implement alerts by notifying on every UI change, received packet, receipt, group-control success or unread-count change. A connection/permission icon does not prove messages will arrive while disconnected or after Android stops the process.

### Vertical slices and acceptance

1. **N1 — committed incoming event seam.** Trace radio and hub producers into durable person/group message storage. Define an after-commit event that identifies a fresh eligible message without placing plaintext in generic logs. Start with person text/replies, then integrate private-group text/replies before declaring the planned alert scope complete.
   - New committed incoming messages are eligible once; transaction rollback, duplicate packets and replay do not create alerts.
   - Own sends, ACKs/receipts, reactions, profile/key/roster changes, invitation control traffic, picture fragments and restored/shared historical rows do not masquerade as new text alerts.
2. **N2 — preference, permission and notification UI.** Add feature-specific opt-in, contextual Android notification permission request and a separate incoming-message channel. Permission denial/revocation and app/channel blocking leave message storage and manual use working. Do not enable background listening just because notification permission was granted.
   - Default content is generic and lock-screen content/presence is hidden; sender, group, message, image and language previews are not exposed by default.
   - No automatic voice playback or sound/vibration demonstration. Any audible-option test needs fresh consent.
   - Explicit immutable tap intents open the intended app/chat through normal unlock. Deleted chats, reused intent identities and multiple pending alerts are handled safely.
   - Suppress the currently visible conversation; coalesce other alerts without erasing unrelated unread state. Dismissing an alert does not delete message history.
3. **N3 — explicit listening contract.** Specify opt-in listening for direct-radio and trusted-hub paths without requiring a hub enrollment merely to listen to a paired radio. Reuse the connected-device lifecycle where appropriate rather than misusing a short planned-send service.
   - Starting/stopping is user-controlled; stopping cancels owned retries and connection work. Do not force battery exemptions or bypass system/user stop choices.
   - Document and exercise Home, screen lock, Recents swipe, process loss, Active apps Stop, Settings Force stop, reboot, permission loss and route disconnect/reconnect as distinct states.
   - No always-on/immediate delivery, auto-reboot or pre-unlock guarantee is implied. A narrower hub-only first slice remains incomplete against this direct-radio-plus-hub target unless the owner approves a scope amendment.
4. **N4 — physical and power qualification.** On the actual supported old and modern Android branches, qualify direct BLE-radio, hub Wi-Fi and hub BLE separately. Use independent senders and exact candidate APKs. Record sender, durable receive and alert timestamps rather than treating queue submission as delivery.
   - Test natural idle/Doze, unavailable hub/radio, recovery, deduplication, shade/lock-screen privacy and tap behavior.
   - Define latency and acceptable incremental battery-drain thresholds before qualification; leave them unresolved until a measured baseline and owner acceptance exist. Do not fabricate numeric battery promises.
   - Obtain explicit consent for any forced-idle/system-state, sound or real-radio test that needs it.

Likely existing paths: `android/app/src/main/java/org/phonemesh/app/{AppCore,AppMailStore,AppGroupStore,HubRoaming,Settings,SettingsActivity,ConversationActivity,ScreenActivity,DeviceAccess}.kt`, app manifest/resources and existing person/group/hub/settings tests. New notifier/event classes and tests are proposed outputs, not pre-existing dependencies. Full call paths, including hub cursor commit, must be traced before defining interfaces.

**N1 implementation (2026-11-05, branch `release/v0.1.3-dev-20261105`; emulator evidence only).** `IncomingAlerts` is a durable
event table (`incoming_alerts`, History schema 24: message id, chat id, commit time — no words, names or pictures). The only
producers of live incoming private text record into it inside the transaction that stores the message: `AppMailStore.project`
(person `Text`/`Reply`) and `AppGroupStore.message` (private-group `Text`/`Reply` that were not shared on joining). Rollback,
including the hub-letter transaction that also moves the cursor and the group change savepoint, removes the event with its
message; an event that cannot be kept undoes its message and leaves the receiving key unconsumed. `take()` hands events out at
most once, oldest first, never inside a transaction, re-checks the message is still a live incoming private text, and drops
deleted messages' events; pending events are capped at the newest 200. `AppCore` hands them to `incomingAlertSink` after
each committed `MESSAGES`/`DELIVERY` change; with no sink they are dropped, not saved for later. Excluded by construction and,
where marked, by test: own sends (test), receipts (test), reactions (person and group tests), profile updates (test), group
creation/join notes and invitations (tests), shared recent history (test), duplicates/replays across restart (test), pictures
(no record call; `record` refuses non-text), the public shared channel and legacy stock-radio chats (not private chats), and
restored/archived copies (they never write live incoming rows). Upgrading creates an empty table, so existing unread messages
raise nothing (test). A crash after `take()` loses only the alert; the message stays unread. N2 supplies the notifier, opt-in,
permission/channel and visible-chat suppression; nothing user-visible changes in N1.

**N2 implementation (2026-11-05, same branch; emulator evidence only).** Settings has an Alerts section: an opt-in switch

## G: relayed group-key/control delivery

### Current constraint

`core/group/GroupPost.kt` resolves private control senders and recipients through contacts, refuses a new epoch when a member is not a contact and queues epoch keys in private bodies. Leaving notices similarly depend on a known admin. Existing `GroupMembers`, roster digests, epochs and group signing keys carry important trust and outsider-deniability choices. Removing the contact guard alone is unsafe.

### Vertical slices and acceptance

1. **G1 — protocol/security design gate.** Specify final-recipient key establishment, authenticated logical admin, group/epoch/parent binding, relay admission and expiry/retry budgets. Compare reuse of existing authenticated sessions/group-only channels with new envelopes. Pin a construction only after source-based review and explicit handling of trust changes.
   - A forwarding peer or hub is transport, not authority. Nonmember infrastructure learns no replacement secret. Members gain no rights beyond their authorized roster.
   - Never protect a replacement epoch secret solely with the old shared group key: a removed member knows it.
   - Preserve explicit Join consent, roster/epoch validation, secret storage protections and the accepted outsider-deniability model. Do not auto-create personal contacts.
   - Define mixed-version v0.1.2/v0.1.3 refusal, migration, recovery and user-facing incompatibility. No unsafe fallback or silent protocol downgrade.
2. **G2 — smallest adversarial topology.** Add deterministic tests with an original admin who knows everyone, a promoted admin lacking one existing member as a contact, and a retained relay route. Prove rekey/removal/admin changes without address-book expansion; then test removed/stale relays, wrong origin/recipient/group, replay, reordered/lost control traffic, offline members, conflicts and crash/restart.
3. **G3 — maintained producer/transport/storage integration.** Land the reviewed mechanism in the real group/postman/store path. Bound pending envelopes and retries, commit state before emission, avoid nonce/chain-position reuse and disclose transport status truthfully. Tests must exercise real construction/verification, not only fake routing.
4. **G4 — ordinary group journey.** Integrate visible administration and recovery states and correct two-person last-admin departure. Existing-group text, receipts, photos, recent-history sharing and backup regressions remain required. A restored history archive must never regain live group keys or membership.
5. **G5 — exact-candidate review and physical qualification.** Review the new protocol/code with positive and targeted negative controls, then exercise multi-phone group transitions on real supported transports. Do not reuse earlier v0.1.2 crypto review as sign-off for changed protocol bytes. Record review type and limitations; a mandatory new human audit is not presumed.

Likely existing paths: `android/core/src/main/kotlin/org/phonemesh/core/group/{GroupMembers,GroupPost,GroupChains,GroupCipher}.kt`, affected wire/session/mail interfaces, `AppCore`, `AppGroupStore`, `GroupRows`, group screens, group tests and group-vector fixtures. A byte-format change requires a mechanical consumer sweep and full regression, not only the named files.

**G1 design (2026-11-06, PROPOSED, not pinned):** `docs/specs/2026-11-06-relayed-group-control-design.md`. From the
source, it compares today's rule, forwarding through a member who knows both, the new secret under the old epoch
(rejected), a sealed envelope carried by the group, and group-scoped sessions. It proposes an envelope sealed to a
separate per-member group box key (ECDH + HKDF + AES-GCM), sent on the admin's own chain of the epoch the recipient
holds, authenticated by the admin's group signature and place on the recipient's list, then taken through the
unchanged `receiveKey` rules; private keys stay the path for contacts, and v0.1.2 members are reached only privately.
It also specifies relayed Ask and Leave, retry limits, saved-state compatibility and the G2 tests. The owner answered
D1a, D2a, D3a and D5a on 2026-11-06 (accounts decision 79): this construction, with the trust change; and, after a
trade-off review (the note's "D4 trade-offs"), D4a (decision 80): envelopes only where needed, no padding, the visible
metadata told plainly. G2/G3 may start. Each G2/G3 slice needs, on its exact source bytes: tests seen failing first and
then passing; positive and negative controls for each refusal (origin, recipient binding, group/epoch/parent, box-key
ownership, replay, no partial change); mutants that those tests catch; vectors from a second implementation written
from the note; a passing maintained gate before its commit; and, before release, the G5 review. The two-person
last-admin departure fix is listed there as separate G4 input without a trust change.

**G3a, the envelope body (2026-11-06, same branch; host JVM evidence only).** `GroupEnvelope` seals one op 8 body
(120 bytes) to a member's box key and opens it back into the `GroupKey` it replaces, binding the group, next epoch,
admin, recipient, box key and ephemeral key. `GroupEnvelopeTest` (12 tests) was seen failing first against a stub (5
positive tests failed; the 7 refusals passed against a stub that refuses everything) and then passing. Ten mutants of
its bindings and checks are each caught by their own test; a first round missed three (recipient, admin and group
left unbound on both sides) because those refusal tests had no positive control, so the tests now open each body for
the right parameters before refusing the changed one. Vectors come from a second implementation written from the
design note (pyca/cryptography, same author). Not yet wired into `GroupPost`: no envelope is sent or read, no box key
exists, and the app's behaviour and wire traffic are unchanged.

**G3b, the announced group box key (2026-11-12, same branch; host JVM evidence only).** `GroupBoxKey` builds and reads
one op 9 body (35 bytes: op 9, version 1, the 33-byte compressed public key) and `GroupBoxKeys` keeps, per member of the
list held, the newest key that member announced on its own radio chain. The body names no owner: the announcing member
is the chain the body travels on, signed with that member's group signing key, so op 9 carries no cryptography of its
own. A key belongs to one member: another member announcing it is refused, and the claim survives that member rotating
the key or leaving the list, because a member that left still holds the private half. "Newest" is the chain position,
not the order the packets arrived in, since a reader may open a later position before an earlier one inside its reading
window. `GroupBoxKeyTest` (23 tests) was seen failing first against a stub (12 failed; the refusals that passed were
those a refuse-everything stub passes) and then passing. Seventeen mutants of the layout, the refusals and the ownership
rules are each caught by their own test; a first round left four survivors, which found three missing tests and one real
design fault — "newest by order of arrival" was wrong, and it is now the chain position. Vectors come from a second
implementation written from the design note (`v013/g3b-boxkey-vectors.py`, same author). Not yet wired into `GroupPost`:
no announcement is sent or read, the private half is not made or kept by the Vault, the keys are not saved, and the app's
behaviour and wire traffic are unchanged. Measured on a forced full rebuild of the unsigned release builds, the APKs are
unchanged (arm64 16,803,748 B, armeabi-v7a 14,794,046 B): R8 strips classes nothing references, so this slice adds 0 B
per ABI and the build ceilings in `android/gradle.properties` do not move.

**G3c, which path an admin uses (2026-11-12, same branch; host JVM evidence only).** `GroupReach` decides, for each
other member of the next list, how the admin reaches it with the new epoch's key: a contact over the private session as
today (which works with a v0.1.2 member), otherwise in an envelope sealed to the box key that member announced on the
list held, otherwise not at all. One member that cannot be reached stops the whole change: nothing is sent to anyone,
because a change that reaches some members and not others would leave the group half in one epoch and half in another.
The admin's own key is not part of this: it holds it itself. `GroupReachTest` (11 tests) was seen failing first against
a stub that makes every member unreachable (5 failed; the refusals that passed were those a refuse-everything stub
passes) and then passing. Twelve mutants of the path rules are each caught by their own test; the one survivor found
the last missing test, that the box key handed out must be a copy. Not yet wired into `GroupPost`: the plan is computed
but no envelope is sent, the admin's old chain positions and the retries are not built, and the app's behaviour and wire
traffic are unchanged. As with G3b, R8 strips these unwired classes, so this slice adds 0 B per ABI and the build
ceilings do not move.

**G3d, the announced box key is read and kept (2026-11-12, same branch; host JVM evidence only).** A member announces its
box key on the radio chain it writes on, so the announcement is bound to that member by the group signature every packet
carries; another member reads it there and keeps it as that member's key. Op 9 is not something people say: it is shown
to nobody and receipted by nobody, and it travels on the radio chain only. A key of a member that leaves the list is
dropped, and the claim stays, so nobody else may take it. The keys are now saved with the group state: the saved
extension is version 2 and carries them, a v0.1.2 save (version 1) loads with no keys, and a key of a member that is not
on the list held is not loaded. `GroupAnnounceTest` (13 tests) was seen failing first against a stub that keeps no key
(5 failed; the refusals that passed were those a refuse-everything stub passes) and then passing; `GroupBoxKeyTest` grew
by four tests for the saving. Twenty mutants of the reading, the ownership rules and the saving are each caught by their
own test; the first round's five survivors found three missing tests (a forged op 9 on the hub chain, an unknown
extension version, and a claimed key after a restart) and one design fault, that the list check was written twice. The
prepared v0.1.2 candidate core (its group core unchanged since `10492845`) reads a v0.1.3 announcement as it must: no
event, no receipt, and the position consumed. Not yet wired into `GroupPost`: the private half is not made or kept by the
Vault, no announcement is sent, and the app's behaviour and wire traffic are unchanged. Unlike G3b and G3c, this slice adds
bytes: `GroupBoxKeys` is now reached from `GroupMember`, which the app uses, so R8 cannot strip it. Measured on a forced
full rebuild of the unsigned release builds, it adds 996 B per ABI (arm64 16,804,744 B, armeabi-v7a 14,795,042 B), so
the arm64 build ceiling rose by 1,000 B to 16,805,000 B under decision 78. The growth over the prepared candidate is
8,244 B per ABI of the 262,144 B allowance.

**G3e, the envelope is read on the admin's chain and the key is taken (2026-11-13, same branch; host JVM evidence
only).** A member reads an envelope (op 8) on the admin's radio chain and takes the key. The packet opened on the
admin's chain, so the group signature shows it is the admin's, and the admin is checked against the list held. The body
is opened with this phone's own box keys, newest first, the current one and then the one before it while it is kept; a
key that does not open is not this phone's and is dropped without a word. What opens goes through the unchanged
`receiveKey` rules: next epoch only, parent = the list held, one waiting key per admin, the 72-hour waiting limit,
conflicts and the 6-hour rival window. An envelope is shown to nobody and receipted by nobody, like a box key
announcement. `GroupEnvelopeTransportTest` (13 tests) was seen failing first against a stub that opens no envelope
(4 failed; the refusals that passed were those a refuse-everything stub passes) and then passing. Twenty mutants of
the reading, the ownership rules and the kept keys are each caught by their own test; the first round's four survivors
found three missing tests (a member that is no longer an admin, the keep window's last moment, and the sender's own
entry in the list) and one mutant that could not be told apart from the right code, because the group is bound by the
AEAD itself. The prepared v0.1.2 candidate core (its group core unchanged since `10492845`) reads a v0.1.3 envelope as
it must: no event, no receipt, and the position consumed. Not yet wired into `GroupPost`: the private half is not made
or kept by the Vault, no envelope is sent, and the app's behaviour and wire traffic are unchanged. Measured on a forced
full rebuild of the unsigned release builds, it adds 276 B per ABI (arm64 16,805,020 B, armeabi-v7a 14,795,318 B), so
the arm64 build ceiling rose by 1,000 B to 16,806,000 B under decision 78. The growth over the prepared candidate is
8,520 B per ABI of the 262,144 B allowance.

**G3f, the admin seals the envelope (2026-11-13, same branch; host JVM evidence only).** An admin that is not a
member's contact seals the new epoch's key to the box key that member announced on the list held, and sends it as a
group packet on its own radio chain of the epoch the member holds, before it takes the new epoch: the member reads it
on the chain it already reads. The key is sealed to the box key the admin read on that member's own chain, which the
group signature every packet carries binds to that member; the admin cannot be told to seal it to any other key. A
member reached by an envelope gets no private key: each is reached one way or the other. Each envelope has its own
ephemeral key, so each AES key and nonce is used once. A member that announced no box key, a member that is not on the
next list, the admin itself, a second envelope to the same member, and an admin that leaves are each refused.
`GroupEnvelopeSealTest` (12 tests) was seen failing first against a stub that seals no envelope (6 failed; the
refusals that passed were those a refuse-everything stub passes) and then passing. Fourteen mutants are each caught by
their own test; the first round's four survivors found one gap in the test (the envelope body is inside the chain
packet, so the ephemeral key was never visible), two rules masked by a later check, and one mutant that was a
tautology. The prepared v0.1.2 candidate core reads the envelope the v0.1.3 admin sealed through the real producer
path as it must: no event, no receipt, and the position consumed. Not yet wired into `GroupPost`: the private half is
not made or kept by the Vault, no envelope is sent, and the app's behaviour and wire traffic are unchanged. Measured
on a forced full rebuild of the unsigned release builds, it adds 364 B per ABI (arm64 16,805,384 B, armeabi-v7a
14,795,682 B), which stays under the ceilings set for G3e, so no ceiling rose for it. The growth over the prepared
candidate is 8,884 B per ABI of the 262,144 B allowance.

**G4a, a group of two ends when one person leaves (2026-11-06, same branch; host JVM and emulator evidence only).**
Either person leaving a two-person group tells the other privately when they are contacts (an admin first; the only
admin now tells the one other person instead of nobody). That phone takes the notice only if it names the epoch it
holds, no newer key waits and nobody invited may still join; its group then ends (`GroupMember.State.ENDED`, stored
after the earlier states), with the note "&lt;name&gt; left. The group has ended.", the conversation line "This group
has ended." and **Delete chat**. With someone invited, the admin's next epoch adds them without the leaver (that epoch
used to fail on a one-person list). v0.1.2 receivers are unchanged; a non-contact is not told until G2/G3. It adds
908 B per ABI to the unsigned release APKs (arm64 16,803,748 B), so the arm64 build ceiling rose by 1,000 B to
16,804,000 B under decision 78.

## W: Windows Bluetooth hub support

A real Windows machine is available by owner confirmation. Its OS/build, adapter/driver, architecture, peripheral-role capability and access details are still discovery inputs, not established compatibility.

1. **W1 — early physical falsifier.** On that real machine, check the LE peripheral role and selected WinRT execution model. Prove connectable service publication, UUID-filtered Android discovery, subscription, response-write, targeted notification and same-process IPv4 loopback access. Record actual advertisement contents; do not expose personal PC names by accident.
   - Bluetooth headphone/client support is not peripheral-mode proof. An API flag is necessary but not a complete pass.
   - No unapproved admin loopback exemption, broad firewall opening, driver install, LAN detour or private-data test substitute.
   - A disposable echo probe is feasibility evidence, not TLS, mail, serial-radio or delivery qualification.
2. **W2 — bounded compatible companion.** Select one justified desktop deployment route after W1. A small .NET/WinRT or C++/WinRT companion is a candidate, not an already-chosen runtime dependency. Port the existing Kotlin/Swift/Python framing contract: UUID derivation, response writes, client-targeted notifications, two streams, sequence/credit checks, bounded queues, deadlines, stale-callback fences and teardown.
   - Clamp complete frames to the actual client MTU/notification limit before calling Windows; never rely on OS truncation.
   - One active phone initially, but target its notifications so a second subscriber cannot receive/inject into its stream.
   - Upstream is the explicitly configured same-host loopback port. TLS remains phone-to-JVM; the bridge holds no hub private key and logs no payload.
3. **W3 — operator artifact.** Supply a runnable per-user foreground companion with clear dependencies, launch/stop/diagnostics, checksum and licence/source information. Preserve hub identity/data and verify Windows ACLs. No unattended service, automatic hotspot/firewall setup or multi-phone support claim.
4. **W4 — complete Windows hub journey.** Qualify pin success and wrong-pin refusal, framing/MTU limits, second-phone isolation, adapter off/on, sleep/resume, companion/JVM restart and stale callbacks. With separate radio permission, prove COM-port radio handling and bidirectional real phone-hub-radio delivery, mailbox/retry/restart semantics and honest Reached hub versus Delivered states.
   - Wi-Fi remains the only bulk update transport; Windows BLE does not solve hotspot/gateway behavior.
   - State support only for the tested Windows/build/architecture/adapter combinations and client scope. Preserve limitations and unsuccessful attempts.

New Windows companion directory and platform tests are future outputs. Existing authorities: `hub-ble-bridge/`, `hub-ble-bridge-linux/`, `android/core/.../hub/{HubGatt,HubEngineTls}.kt`, `android/radio-ble/.../GattHubCentral.kt` and `android/hub/`.
