# v0.1.3 release plan: background messaging and easier groups

Status: **DRAFT implementation plan; feature direction approved, implementation not started.**

## Authority and baseline

The owner agreed on 2026-11-04 to plan incoming-message notifications, relayed group-key delivery and Windows Bluetooth hub support. A real Windows machine will be available for testing. **TalkBack belongs in a later release.** These decisions supersede treating Windows hardware availability as unknown or TalkBack as a v0.1.3 candidate. Availability is not yet adapter capability or qualification.

Baseline inspected: public v0.1.2 source `24df21d0880443bdb5bb83ba20b48881e5ce6315`, production Android version 0.1.2/code 3. v0.1.1 remains the latest stable release at planning time; v0.1.2-demo.1 is a separate simulated-radio pre-release. Rebase this plan onto the eventual signed v0.1.2 source before implementation. Do not change the v0.1.2 candidate's wire formats or defaults to start this work.

This document authorizes no private-key handling, release/tag/publication, radio writes, microphone capture/playback, Windows installation/driver/firewall changes or new recurring/paid resources. Existing consent and publication boundaries remain. It does not select a cryptographic construction merely by naming a goal.

## Outcome and scope

A person can receive private-chat and private-group text alerts with the screen closed under an explicitly supported listening mode; a promoted group admin can manage existing members without adding everybody as personal contacts; and a qualified Windows laptop can expose the existing local hub over Bluetooth.

### Planned deliverables

- **N — Notifications and receiving lifecycle:** private one-to-one and private-group text/reply alerts; explicit opt-in listening; truthful connected/disconnected state; privacy-safe notification content and navigation.
- **G — Relayed group management:** securely deliver group control/key updates to already-admitted members without requiring every admin to have all members as personal contacts; retain consent and current group-size limit; fix the documented two-person last-admin departure behavior.
- **W — Windows Bluetooth hub companion:** one active phone initially, existing pinned-TLS hub protocol, runnable per-user foreground companion and real Windows/Android qualification.
- **R — Release integration:** data-preserving upgrade from signed v0.1.2, demo coverage, source/build/licence/size/network gates, exact artifact identity and honest supported-platform statements.

Windows is a planned workstream with an early hardware gate. If the available machine/adapter cannot support the required role, preserve the failure and request a specific owner disposition; do not silently drop support or claim an untested replacement. Independent Android work may continue. Do not let an unresolved Windows experiment automatically turn into indefinite release delay.

### Explicit non-goals

TalkBack; larger groups; username/directory or multi-account features; social recovery; automatic backup hosting; app/APK updates through hubs; local-language speech/model deployment; quiet-radio configuration or coverage wizard; cross-zone radio conversion; quantum-safe protocol changes; voice imprints; typing/seen indicators; edit/delete-for-everyone; location sharing; cloud push; notification quick reply; bulk Bluetooth updates; unattended Windows services; automatic driver/hotspot/firewall setup.

Local-language review and quiet-radio/coverage planning may proceed as separately authorized pilot preparation, not hidden v0.1.3 acceptance requirements. Existing accessibility and English/French support must not regress despite TalkBack being deferred.

## N: incoming alerts and background listening

### Current implementation and constraints

`AppCore`, `AppMailStore` and `AppGroupStore` already receive and durably store messages. `changed(Change.MESSAGES)` is a broad screen-observer signal, not a fresh-incoming-message event. The manifest already declares notification and connected-device foreground-service permissions. `HubRoaming` supplies a real opt-in foreground service; its executable lifecycle can retain/reconnect a stock-radio link, but activation currently requires a saved hub. It returns `START_NOT_STICKY`; no boot receiver provides automatic boot reception.

Do not implement alerts by notifying on every UI change, received packet, receipt, group-control success or unread-count change. A connection/permission icon does not prove messages will arrive while disconnected or after Android stops the process.

### Vertical slices and acceptance

1. **N1 — committed incoming event seam.** Trace radio and hub producers into durable person/group message storage. Define an after-commit event that identifies a fresh eligible message without placing plaintext in generic logs. Start with person text/replies, then integrate private-group text/replies before declaring the planned alert scope complete.
   - New committed incoming messages are eligible once; transaction rollback, duplicate packets and replay do not create alerts.
   - Own sends, ACKs/receipts, reactions, profile/key/roster changes, invitation control traffic, picture fragments and restored/shared historical rows do not masquerade as new text alerts.
2. **N2 — preference, permission and notification UI.** Add feature-specific opt-in, contextual Android notification permission request and a separate incoming-message channel. Permission denial/revocation and app/channel blocking leave message storage and manual use working. Do not enable background listening just because notification permission was granted.
   - Default content is generic and lock-screen content/presence is hidden; sender, group, message, image and language previews are not exposed by default.
   - No automatic voice playback or sound/vibration demonstration. Any audible-option test needs fresh consent.
   - Explicit immutable tap intents open the intended app/chat through normal unlock. Deleted chats, reused intent identities and multiple pending alerts are handled safely.
   - Suppress the currently visible conversation; coalesce other alerts without erasing unrelated unread state. Dismissing an alert does not delete message history.
3. **N3 — explicit listening contract.** Specify opt-in listening for direct-radio and trusted-hub paths without requiring a hub enrollment merely to listen to a paired radio. Reuse the connected-device lifecycle where appropriate rather than misusing a short planned-send service.
   - Starting/stopping is user-controlled; stopping cancels owned retries and connection work. Do not force battery exemptions or bypass system/user stop choices.
   - Document and exercise Home, screen lock, Recents swipe, process loss, Active apps Stop, Settings Force stop, reboot, permission loss and route disconnect/reconnect as distinct states.
   - No always-on/immediate delivery, auto-reboot or pre-unlock guarantee is implied. A narrower hub-only first slice remains incomplete against this direct-radio-plus-hub target unless the owner approves a scope amendment.
4. **N4 — physical and power qualification.** On the actual supported old and modern Android branches, qualify direct BLE-radio, hub Wi-Fi and hub BLE separately. Use independent senders and exact candidate APKs. Record sender, durable receive and alert timestamps rather than treating queue submission as delivery.
   - Test natural idle/Doze, unavailable hub/radio, recovery, deduplication, shade/lock-screen privacy and tap behavior.
   - Define latency and acceptable incremental battery-drain thresholds before qualification; leave them unresolved until a measured baseline and owner acceptance exist. Do not fabricate numeric battery promises.
   - Obtain explicit consent for any forced-idle/system-state, sound or real-radio test that needs it.

Likely existing paths: `android/app/src/main/java/org/phonemesh/app/{AppCore,AppMailStore,AppGroupStore,HubRoaming,Settings,SettingsActivity,ConversationActivity,ScreenActivity,DeviceAccess}.kt`, app manifest/resources and existing person/group/hub/settings tests. New notifier/event classes and tests are proposed outputs, not pre-existing dependencies. Full call paths, including hub cursor commit, must be traced before defining interfaces.

## G: relayed group-key/control delivery

### Current constraint

`core/group/GroupPost.kt` resolves private control senders and recipients through contacts, refuses a new epoch when a member is not a contact and queues epoch keys in private bodies. Leaving notices similarly depend on a known admin. Existing `GroupMembers`, roster digests, epochs and group signing keys carry important trust and outsider-deniability choices. Removing the contact guard alone is unsafe.

### Vertical slices and acceptance

1. **G1 — protocol/security design gate.** Specify final-recipient key establishment, authenticated logical admin, group/epoch/parent binding, relay admission and expiry/retry budgets. Compare reuse of existing authenticated sessions/group-only channels with new envelopes. Pin a construction only after source-based review and explicit handling of trust changes.
   - A forwarding peer or hub is transport, not authority. Nonmember infrastructure learns no replacement secret. Members gain no rights beyond their authorized roster.
   - Never protect a replacement epoch secret solely with the old shared group key: a removed member knows it.
   - Preserve explicit Join consent, roster/epoch validation, secret storage protections and the accepted outsider-deniability model. Do not auto-create personal contacts.
   - Define mixed-version v0.1.2/v0.1.3 refusal, migration, recovery and user-facing incompatibility. No unsafe fallback or silent protocol downgrade.
2. **G2 — smallest adversarial topology.** Add deterministic tests with an original admin who knows everyone, a promoted admin lacking one existing member as a contact, and a retained relay route. Prove rekey/removal/admin changes without address-book expansion; then test removed/stale relays, wrong origin/recipient/group, replay, reordered/lost control traffic, offline members, conflicts and crash/restart.
3. **G3 — maintained producer/transport/storage integration.** Land the reviewed mechanism in the real group/postman/store path. Bound pending envelopes and retries, commit state before emission, avoid nonce/chain-position reuse and disclose transport status truthfully. Tests must exercise real construction/verification, not only fake routing.
4. **G4 — ordinary group journey.** Integrate visible administration and recovery states and correct two-person last-admin departure. Existing-group text, receipts, photos, recent-history sharing and backup regressions remain required. A restored history archive must never regain live group keys or membership.
5. **G5 — exact-candidate review and physical qualification.** Review the new protocol/code with positive and targeted negative controls, then exercise multi-phone group transitions on real supported transports. Do not reuse earlier v0.1.2 crypto review as sign-off for changed protocol bytes. Record review type and limitations; a mandatory new human audit is not presumed.

Likely existing paths: `android/core/src/main/kotlin/org/phonemesh/core/group/{GroupMembers,GroupPost,GroupChains,GroupCipher}.kt`, affected wire/session/mail interfaces, `AppCore`, `AppGroupStore`, `GroupRows`, group screens, group tests and group-vector fixtures. A byte-format change requires a mechanical consumer sweep and full regression, not only the named files.

## W: Windows Bluetooth hub support

A real Windows machine is available by owner confirmation. Its OS/build, adapter/driver, architecture, peripheral-role capability and access details are still discovery inputs, not established compatibility.

1. **W1 — early physical falsifier.** On that real machine, check the LE peripheral role and selected WinRT execution model. Prove connectable service publication, UUID-filtered Android discovery, subscription, response-write, targeted notification and same-process IPv4 loopback access. Record actual advertisement contents; do not expose personal PC names by accident.
   - Bluetooth headphone/client support is not peripheral-mode proof. An API flag is necessary but not a complete pass.
   - No unapproved admin loopback exemption, broad firewall opening, driver install, LAN detour or private-data test substitute.
   - A disposable echo probe is feasibility evidence, not TLS, mail, serial-radio or delivery qualification.
2. **W2 — bounded compatible companion.** Select one justified desktop deployment route after W1. A small .NET/WinRT or C++/WinRT companion is a candidate, not an already-chosen runtime dependency. Port the existing Kotlin/Swift/Python framing contract: UUID derivation, response writes, client-targeted notifications, two streams, sequence/credit checks, bounded queues, deadlines, stale-callback fences and teardown.
   - Clamp complete frames to the actual client MTU/notification limit before calling Windows; never rely on OS truncation.
   - One active phone initially, but target its notifications so a second subscriber cannot receive/inject into its stream.
   - Upstream is the explicitly configured same-host loopback port. TLS remains phone-to-JVM; the bridge holds no hub private key and logs no payload.
3. **W3 — operator artifact.** Supply a runnable per-user foreground companion with clear dependencies, launch/stop/diagnostics, checksum and licence/source information. Preserve hub identity/data and verify Windows ACLs. No unattended service, automatic hotspot/firewall setup or multi-phone support claim.
4. **W4 — complete Windows hub journey.** Qualify pin success and wrong-pin refusal, framing/MTU limits, second-phone isolation, adapter off/on, sleep/resume, companion/JVM restart and stale callbacks. With separate radio permission, prove COM-port radio handling and bidirectional real phone-hub-radio delivery, mailbox/retry/restart semantics and honest Reached hub versus Delivered states.
   - Wi-Fi remains the only bulk update transport; Windows BLE does not solve hotspot/gateway behavior.
   - State support only for the tested Windows/build/architecture/adapter combinations and client scope. Preserve limitations and unsuccessful attempts.

New Windows companion directory and platform tests are future outputs. Existing authorities: `hub-ble-bridge/`, `hub-ble-bridge-linux/`, `android/core/.../hub/{HubGatt,HubEngineTls}.kt`, `android/radio-ble/.../GattHubCentral.kt` and `android/hub/`.

## Integration, ordering and release requirements

- Keep v0.1.2 release work isolated. Resolve its legacy stock-chat reply scope separately; this plan does not silently move decision 39 to v0.1.3.
- Rebase onto the eventual signed v0.1.2 source and record branch/commit/tree before implementation. Maintain source/state compatibility and a safe same-signer upgrade. Do not invent compatibility with an untested new group wire format.
- Begin N1 and G1 independently; run W1 as soon as the owner supplies the Windows access/test session. These are separate implementation boundaries, not a mandate for simultaneous builds or extra agents.
- Land behavior in small TDD slices with integrated consumers. Freeze shared interfaces before parallel writers touch them; respect any active one-writer/resource restriction.
- Freeze and qualify one combined candidate only after selected landings finish. Do not package a candidate while source writers are still active.
- Run maintained `scripts/check.sh`, then affected instrumentation, demo journeys and physical checks on exact frozen bytes. Current canonical command needs Java 17, Android SDK 35, NDK 28.2.13676358, CMake 3.22.1, pinned sherpa runtime and the repository's locked Python toolchain. Derive selected test counts from actual runner/test inventory, not this plan.
- Extend English/French help and demo for new alert/listening/admin states. Preserve demo-only simulated people/radios, production secure screens, pack trust and no-cloud boundaries. Existing screenshot/accessible-name tests remain; full TalkBack stays deferred.
- Measure both ABI APK sizes and any new runtime/platform package sizes. A size-ceiling increase or new security trust model requires a recorded owner decision rather than a silent override.
- Validate signed APK identity, version and source binding; prove signed v0.1.2-to-v0.1.3 data preservation, not just schema-fixture migration. Owner signing and public release approval remain separate.

## Decisions and open inputs

**Resolved:** three feature workstreams; real Windows hardware will be available; TalkBack is deferred; no broad optional backlog expansion; Windows has an early capability gate and no untested support claim.

**Draft target, not yet product-qualified:** standalone direct-radio plus hub listening. If implementation discovery shows this needs a material scope/permission/battery change, return one concrete proposal rather than silently shipping hub-only notifications.

**Still needed before the relevant stage:** Windows access/test session and actual adapter facts; G1 construction/compatibility acceptance; notification latency/battery acceptance bands after a measured baseline; disposition of v0.1.2 legacy stock-chat replies. These do not prevent drafting or dependency-independent work.
